# Release and migration policy

This policy applies to every change, including the initial release and everything after it. Plan approval is not production approval. Ordinary delivery is a pull request, required CI, one independent review, and a merge to `main` by the implementation owner after that review approves. The merge runs development deployment. Production stays on the manual gate below.

Development delivery runs migrations and runtime provisioning only when reviewed migration inputs changed since the last successful development delivery. Those inputs are the `src` tree, the `scripts` tree, `supabase/migrations`, `.github/workflows/apply-development-migrations.yml`, `.github/actions/setup`, `package.json`, `pnpm-lock.yaml`, and `.nvmrc`. Covering the whole source and scripts trees is deliberate: a later change anywhere in those trees takes the migration path, including a change that does not affect provisioning. That keeps package, lockfile, Node, and setup changes on the migration path without a dependency checker. A push with no change in that set still deploys and smoke-tests the commit, and it skips the migration job. An ordinary unchanged push therefore does not re-check ledger or privilege drift and does not re-provision `app_runtime`. Manual *Deploy development* or *Migrate development* runs migrations. Use one of those when rotating `APP_RUNTIME_PASSWORD` or repairing development role or ledger drift. A pull request that changes those inputs has to be scoped to authorize the credential and database work provisioning performs. Pull request 20 remains a held draft and is not merged from another issue.

## Production releases

Every production release requires the user's explicit sign-off on the specific candidate and its migration set. That includes future features, fixes, dependency updates and database changes. Completing the initial release does not authorize later production releases.

The user chooses sign-off testing. Routine tests, review and deployment execution stay automated. Coding agents must not deploy production or set `PRODUCTION_RELEASES_ENABLED`.

A candidate reaches production only through `.github/workflows/release-production.yml`: it must already be on `main`, have passed development deployment, pass CI, be approved on the protected `production` GitHub environment, and have `PRODUCTION_RELEASES_ENABLED=true`. Application rollback does not reverse database changes.

## Database migrations

- Migrations live in `supabase/migrations` and are checksummed in `supabase/migrations/manifest.json`.
- Apply the same reviewed files to development before any production consideration. A push to `main` runs CI, then a name-only check of the development Vercel configuration, then those migrations and privilege checks when the inputs above changed, then development deploy, smoke and promotion. A missing publishable key or `TUTOR_MBOS_APP_DATABASE_URL` stops the run before hosted SQL and before promotion. *Migrate development* is only a manual recovery entry. It shares the `development-delivery` concurrency group with `queue: max` and `cancel-in-progress: false`, so a recovery dispatch waits behind an in-progress delivery and does not cancel a delivery that is already queued. Both refuse a production database URL and the `app_runtime` login. Pull requests do not receive migration or deploy secrets.
- Fresh-install and populated-upgrade tests, a failed-migration rollback test, and a target/drift check run in CI without secrets.
- Never edit a migration that has been applied. Add a corrective migration.
- The runner takes a session advisory lock, checks the recorded ledger against the reviewed files, and only then applies each pending file in its own transaction, in manifest order. A recorded version that is not in the reviewed set, a checksum or name that does not match the file, or a history that skips an earlier version stops the run before any pending SQL.
- Destructive changes need a reviewed recovery plan and verified backup coverage. Emergency fixes do not skip these gates unless the user explicitly authorizes the exception.

Development migration credentials are GitHub environment secrets, not repository files and not agent workspace variables. The development deploy and the manual recovery workflow pass these two names into the reusable migration workflow. GitHub leaves an environment secret empty in a reusable workflow unless the caller passes it. The called job keeps `environment: development`, so the passed name resolves to that environment. Before any SQL, the workflow reports each secret as present or absent and does not print the value. When the migration URL is present but is not the development migration login, the apply script stops before opening a connection and prints one reason code (`invalid`, `binding_mismatch`, `app_runtime`, `privileged_user`, or `transaction_pooler`) with setup guidance. It does not print the value, host, username, password, length, hash, or parser error. A missing URL is reported separately and does not use those codes.

The running app uses `TUTOR_MBOS_APP_DATABASE_URL` on the Vercel development project. The username must be `app_runtime`. It is not a `NEXT_PUBLIC_` variable and it is not the migration URL. Requests set the database role to `app_request`, which cannot bypass row level security. The service role is not a business-request client. The migration URL must be a direct or session-mode connection. Port 6543, the transaction pooler, is rejected because the migration lock is session-scoped. The migration login is the documented `postgres` or `supabase_admin` role. It must already be able to execute `auth.uid()` and `auth.jwt()`. The migration does not grant on schema `auth` and does not need a platform superuser or a manual grant from the `auth` owner. `app_request` calls `app.auth_uid()` and `app.auth_jwt()`, security-definer functions owned by the migration login. Development apply checks `has_schema_privilege('authenticated', 'app', 'USAGE')` is false, then in one transaction grants the migration login `SET` on `app_request` by quoting `format('%I', current_user)`, runs `set local role app_request; select app.auth_uid()`, and rolls that grant back. The current_user, current_role, and session_user keywords are not GRANT role specifications: on supabase/postgres 17.6.1.011 that form crashes the backend. A hosted `postgres` login on Postgres 16+ can administer `app_request` without already being allowed to assume it. The call fails, and the original database error is kept, when `app_request` cannot execute `app.auth_uid()`. The migration set does not revoke `authenticated` from schema `auth`, because hosted RLS, Storage and Realtime use those grants.

Development apply then provisions `app_runtime` for the ordinary `postgres` login. It sends neither `NOSUPERUSER` nor `NOBYPASSRLS`. Postgres 16 and later reject a non-superuser statement that edits the SUPERUSER attribute; that detail says only a superuser may change the attribute. The detail that only a superuser may alter roles with the SUPERUSER attribute can mean the target role has `rolsuper`, including when the statement only sets `LOGIN`. The apply uses the flags read from `pg_roles` and prints those flags when it refuses the role. Changing the BYPASSRLS attribute has the matching detail. The apply reads membership options and grantors, effective memberships, the `app_request` flags, roles reachable through `app_request`, and `app_runtime` owner or ACL dependencies. A missing role is created with `LOGIN NOINHERIT` only. An existing safe role may be given `LOGIN` and `NOINHERIT`. `app_request` is granted with `INHERIT FALSE, SET TRUE`, and only that membership's ADMIN option is revoked. A second grantor row stops the run with each row's options and grantor visible. The password is a SCRAM-SHA-256 verifier: SASLprep, then PBKDF2-HMAC-SHA-256 at Postgres 17's `scram_iterations` default of 4096, with a 16-byte salt. The plaintext and the verifier are omitted from the log. Before that verifier is sent and before `app_runtime` is reported ready, the run stops when `app_runtime` has `SUPERUSER`, `BYPASSRLS`, `CREATEROLE`, `CREATEDB`, or `REPLICATION`; when its direct membership is not exactly one `app_request` row with admin false, inherit false, and set true; when `pg_has_role('app_runtime', oid, 'MEMBER')` is not exactly `app_runtime` and `app_request`; when `app_request` can log in, has those restricted attributes, or can reach another role; or when `pg_shdepend` has an owner or ACL row for `app_runtime`. Reviewed grants held by `app_request` on schema `app`, its tables, and its functions, including execute on the migration-owned `app.auth_uid()` and `app.auth_jwt()` wrappers, are the access contract and are not treated as `app_runtime` dependencies. Restricted attributes stay unchanged. The role is not dropped or recreated, and `app_request` is not altered. A database failure names the phase and appends only an SQLSTATE of five letters or digits. It omits the server message, the query, and the password. The log prints each reviewed ledger version, name, and sha256, checks those lines against the reviewed migration set, then prints the role flags, membership options and grantors, effective memberships, `app_request` flags, and the owner or ACL count. The same flags are printed when the role is refused. Already-applied migration files stay unchanged.
